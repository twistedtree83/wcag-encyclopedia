# T-06 — Responsive shell: container queries, 320px, mobile drawer, viewport preview

**Issue:** #6  **Status:** shipped

## What shipped

Full functionality at 320px, the mobile navigation drawer, and the in-page viewport preview —
on one container-query foundation, as the issue specified.

## Decisions made

**Layout responds to a named container, not the window.** The preview frame declares
`container: preview / inline-size`, and the rail/drawer switch is `@container preview
(max-width: 960px)`. This is what makes the preview honest: narrowing the frame runs exactly
the code path a real 320px screen runs. With media queries the preview would resize a box and
change nothing inside it.

**The drawer is a native `<dialog>` opened with `showModal()`.** That buys focus trapping,
Escape to close, inertness of the page behind, and focus restoration to the trigger — all of
which are easy to hand-roll incorrectly, and a hand-rolled focus trap is a common source of
actual keyboard traps (2.1.2). Escape and backdrop clicks both route through one `onClose`, so
React state and the dialog's own open state cannot drift.

**The drawer carries its own search and level filter**, because at this width the masthead has
no room and a reader on a phone still has to be able to filter.

### Three real bugs the tests caught

**1. `.frame` collided with itself.** The preview frame and the fail/pass example frames both
used `.frame`. Renamed to `.preview` / `container: preview`. Worth remembering when adding
components: `frame` means an example frame in this codebase.

**2. Duplicate element ids.** Two `Controls` instances now exist in the DOM — masthead and
drawer — and both emitted `id="criterion-search"`. Only one is ever *exposed* (the masthead
copy is display:none when narrow; the drawer is display:none when closed), but duplicate ids
make `label for` ambiguous regardless of visibility. `Controls` now takes an `idPrefix`. **Any
future component rendered twice needs the same treatment**, and there is an e2e test asserting
no id appears twice with the drawer both open and closed.

**3. The viewport picker used to live inside the frame it resizes.** Selecting Tablet or 320px
narrowed the frame past the breakpoint, which hid the picker — trapping the reader in the
preview with no way back short of a reload. The picker now sits in its own bar *outside* the
frame, which is also where it belongs conceptually: it is chrome around the preview, not
previewed content. There is a regression test that walks every option.

**Selecting 320px opens the drawer**, per the issue. Because the drawer is modal, the picker is
inert until it is dismissed — correct modal behaviour, and the reader gets out with Escape,
the Close button, or a backdrop click.

## Deliberately left

- The preview only narrows; it does not emulate touch, pointer coarseness, or device pixel
  ratio. Those would change what the demos do and are out of scope.
- `useViewport` tracks `window.innerWidth` to decide whether the drawer is applicable, since
  a real narrow window and a narrow preview should behave the same. It is the one place the
  window width is still read.

## Gate

`npm run verify` green: typecheck clean; 91 unit tests; build; **48** Playwright tests (12 new:
rail replaced by the toggle at 320px, drawer focus trapping and Escape, focus returning to the
trigger, search and filter present in the drawer, 44px drawer targets, no horizontal scroll
with the drawer open or closed, full behaviour at 200% zoom, the preview narrowing the whole
page, the drawer opening at 320px, viewport `aria-pressed` state, the picker staying reachable
at every width, and no duplicate element ids).
