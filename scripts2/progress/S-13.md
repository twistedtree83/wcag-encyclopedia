# S-13 — Post: Accessible forms: every criterion a form touches

**Issue:** #81  **Commit:** see the PR (branch `post/s-13-forms`)  **Status:** shipped, waiting on the owner's approval of its PR

## What shipped
One post, `src/blog/posts/accessible-forms.md` (`/blog/accessible-forms/`), published
2026-11-28. It takes the fifteen criteria an ordinary form meets, in the order a person fills
one in: labels, groups and required fields, input purpose, field contrast, On Input, errors and
status messages, error prevention, redundant entry, signing in. It ends with a seven-step check.
It embeds the 3.3.1 examples (`::example{num="3.3.1"}`) and the `form-labels` lab for 3.3.2.

## Decisions made
- Slug `accessible-forms`: short, and not tied to a version or year, so it never needs to change.
- Criteria: 1.3.1, 1.3.5, 1.4.1, 1.4.11, 2.4.6, 2.5.3, 3.2.2, 3.3.1, 3.3.2, 3.3.3, 3.3.4, 3.3.7,
  3.3.8, 4.1.2, 4.1.3. Keyboard criteria (2.1.1, 2.4.3, 2.4.7) are left to S-15. That post covers
  them, and linking them here would add three more "Further reading" entries that say little.
- Embed id clash (shared notes, S-08): the 3.3.1 live examples and the `form-labels` lab build
  every id from `useId()`. The only plain `id="email"` strings are diff text, not DOM ids. So
  the two embeds cannot clash, and axe on the post page confirms it.
- Placeholder as label: W3C's Understanding 3.3.2 treats a placeholder as a hint next to a label
  and does not ban it outright. The post follows the site's 3.3.2 page (a placeholder is not a
  label) and words that as advice, citing W3C only for the hint reading.
- Contrast figures (#d0d0d0 1.54:1, #949494 3.03:1, #767676 4.54:1, each on white) were computed
  with the WCAG relative-luminance formula.
- Every fact was checked against the W3C Understanding pages, the WCAG 2.2 Recommendation
  (53 input purposes), W3C's "What's new in WCAG 2.1" (the versions of 1.3.5, 1.4.11, 2.5.3 and
  4.1.3) and MDN's autocomplete page (token names).

- Two unit tests assumed the blog has no posts. This is the first real post, so they failed.
  I fixed them on purpose and weakened neither:
  - `tests/criterionPage.test.tsx` (anatomy) now expects "Further reading" whenever
    `postsAbout(num, POSTS)` is non-empty.
  - `tests/share.test.ts` now counts one card per post as well as one per criterion.

  The other launch posts (S-11, S-12, S-14 to S-16) will need the same change if they branch
  from `seo` before this one merges. The fix is identical, so a merge conflict there resolves to
  either side.
