# S-06 — Cloudflare Web Analytics

**Issue:** #74  **Commit:** see `git log` (the commit that adds this file)  **Status:** shipped

## What shipped
`CF_ANALYTICS_TOKEN: string | undefined` in `src/site/config.ts`, committed unset. While it is
unset no page carries the beacon; once set, every pre-rendered page ends `<body>` with one
`<script defer src="https://static.cloudflareinsights.com/beacon.min.js" data-cf-beacon="{…token…}">`.
No cookie, no consent banner.

## Decisions made
- The tag is built by `analyticsBeacon(token)` in `src/site/analytics.ts` (attribute-escaped
  JSON). `render(route)` returns it as a new `beacon` field, and `scripts/prerender.mjs` writes
  it into a new `<!--@analytics-->` placeholder at the end of `<body>` in `site.html`, outside
  `#root` so hydration never sees it. It does not go in `head`, which S-01/S-02 own.
- The set case is unit-tested by mocking `src/site/config` (`tests/analytics.test.ts`) over
  every route; the committed (unset) build is checked in `e2e/analytics.spec.ts`, which counts
  `cloudflareinsights` per built page (0 unset, 1 set) without `test.skip`, and checks Home and
  1.4.3 set no cookie and show no cookie/consent text.
- Checked by hand: with a token set, `npm run build` puts exactly one beacon on each page.
- The comment beside the placeholder in `site.html` says "Cloudflare Web Analytics" but not
  `cloudflareinsights`, so the unset check stays exact.

## Deliberately left
- Setting the real token is the step outside the repo (docs/PRD-seo.md): create the site in
  Cloudflare → Analytics & Logs → Web Analytics and set `CF_ANALYTICS_TOKEN`.
- No Content-Security-Policy exists; if one is added, it must allow
  `static.cloudflareinsights.com` (script) and `cloudflareinsights.com` (connect).
